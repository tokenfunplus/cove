# Add answer tools and Generation measurements

Saved answers expose selection-based follow-ups and a Working Draft editor. Side Conversations and workbench revision requests create ordinary local Conversations and use the existing Chat Generation Batch lifecycle, Active Model Set, privacy requirements, browser inference, cancellation, and immutable Context Snapshots. They do not append to or select answers in the main conversation. Ordinary and private inference remain behind their existing boundaries. Only one Batch can be active across the Local Service, including answer tools.

The first side question includes the explicitly chosen passage, source model identifier, and question as reference data. It excludes the rest of the main conversation. Later side questions use that separate conversation's Selected Answers. The same workspace System Prompt and generation parameters apply. Each revision request uses a fresh conversation containing the current working text, optional selected passage, and editing instruction. Switching tool views retains separate follow-up and revision sessions. Opening a tool does not contact a Provider.

Working Draft content and a bounded undo/redo history remain in React state, including while the panel is closed or another main conversation is selected. Refresh protection covers unsent side questions, revision instructions, and changed drafts. Replacing a changed draft requires confirmation. Markdown download and clipboard actions are explicit; drafts are not written to browser storage. A proposed revision must be reviewed and explicitly applied. Selection rewrites replace only the captured textarea range, and a revision cannot overwrite edits made since its request. The original answer and its verification evidence remain immutable. The editor limit is 120,000 UTF-16 code units. Follow-up excerpts are bounded to 8,000 UTF-16 code units.

Schema 17 adds optional JSON Generation Metrics to persisted attempts without backfilling old measurements. Chat measures ordinary requests from opening the Provider stream through completion, records first/last nonempty text arrival, and retains Provider-reported usage. Browser inference reports equivalent browser observations through its existing settlement command, including verification in total elapsed time; these are not independently verified measurements. Input/output counts remain absent when not supplied. Completed-attempt API read models and JSON exports retain measurements. Failed or stopped attempts and older saved answers may have no measurements.

OpenAI-compatible requests ask for streaming usage. A single fallback without that optional field is permitted only for an HTTP 400/422 response explicitly identifying an unsupported `stream_options` or `include_usage` field before any response stream is accepted. Accepted requests, interrupted streams, and unrelated failures are never retried by this fallback. Usage-only chunks with empty choices are valid. No extra Provider request is made merely to obtain missing counts.

The response panel shows first text, total time, reported tokens, and token throughput when an interval is available. Speed divides reported output tokens by the time between first and last nonempty text chunks; it is an observational estimate, not a controlled model benchmark. Optional user-supplied USD rates are browser-local non-secret preferences keyed by Provider/model. Displayed costs use those current rates and exclude Provider-specific cache adjustments, discounts, and other charges.

This extends ADR-0014, ADR-0015, ADR-0019, and ADR-0029 without superseding their ownership or context rules. HTTP remains an adapter, Chat owns generation lifecycles, and SQLite owns local history. Clearing history also clears the window-local answer tools after both generation owners have stopped.
