# Reuse project background through independent Batch snapshots

Status: Accepted and implemented in source. SQLite schemas 23 and 24 add project background reuse and lookup indexes; release scheduling remains separate.

## Scope and motivation

The first version reduces repeated background entry and source attachment across related Conversations. A Project groups Conversations and holds Project Instructions, one editable Project Background text, and fixed Project Sources. Each new Generation Batch captures this shared input independently of its historical Context Snapshot.

Individual memory entries, memory-version tables, save-answer-as-memory actions, extraction, conflict review, full-text/vector source retrieval, and granular historical payload purging are deferred. User-edited instructions and background share an editor workflow while retaining distinct inference roles: instructions guide behavior; background and sources are reference data.

This design does not establish demand across existing users or commit delivery ahead of other beta feedback. Repeated reports of re-entering background and sources would support prioritization. Evaluate actual cross-conversation reuse before expanding into memory management.

## Ownership and storage

HTTP adapts commands and Browser Session authorization. Chat owns project selection, source preparation, context assembly, admission and cancellation. Persistence owns local records, transactional snapshots and deletion. Project data belongs in SQLite rather than browser preferences.

Use a small storage model:

- `projects`: identity, name, description, current instruction text, current background text, monotonic revision and timestamps. Revision supports optimistic concurrency; no project edit-history interface or instruction/background version table is required.
- `conversations.project_id`: nullable current membership, with a membership revision for stale-admission checks. Existing Conversations remain ungrouped.
- `project_sources`: project-owned immutable source entries using `documents.Snapshot` and a reference to original bytes in `project_source_blobs`. Replacement or explicit webpage refresh creates a new entry with the parser-derived snapshot identity. No source-version browser is required.
- `generation_project_contexts`: Batch-owned rendered instructions/reference prefix, rendering version, historical Project identity/revision, source entry/snapshot identities and source metadata/text sections. Execution reads saved text rather than reconstructing it from live references. Normalized Batch-source rows reference the original-byte blobs without copying their payload into each Batch.
- `project_source_blobs`: immutable original bytes keyed by SHA-256 of those bytes. The raw-byte hash is distinct from `documents.Snapshot.ID`, which can include webpage provenance and extraction identity. Project-source rows and Batch-source rows hold foreign-key references to blobs.

Insert/deduplicate blobs and add owning references transactionally. A Batch stores the extracted source text/sections required by inference, citations and export; only original downloads resolve its immutable blob reference. A repeated Batch or copied branch adds references rather than duplicating raw bytes. Deleting an owner removes its references and collects blobs only when neither project-source nor Batch-source references remain, within the same serialized write transaction. Foreign keys prevent premature deletion; test the unreferenced-blob query against every owning table. Preview bytes stay ephemeral until an explicit save or accepted admission, so failed saves/admissions leave no orphan blobs. The first version scopes this storage change to fixed Project Sources; existing turn-attachment storage is unchanged.

Project edits change the current row/revision; accepted Batch payloads and blob references remain immutable. Historical Project/source identifiers are provenance values, not cascading dependencies on deletable live Project/source rows. This bounds raw-file storage by unique original content rather than by the number of turns or branches. Extracted text and rendered request text still occupy space per Batch, and the data-size description must acknowledge that cost.

Project scoping prevents accidental content mixing in this single-user application. It adds no tenant roles. Existing session/CSRF rules remain. A browser-supplied Project identifier is accepted only as the target of an explicit membership command: creating a Conversation in a Project, moving a Conversation, or `Continue in a new conversation`. Chat verifies that the target Project exists and is live, and returns not-found otherwise. `POST /api/conversations` accepts an optional `project_id` for this purpose; it is mutually exclusive with `source_conversation_id`, and omitting both creates an ungrouped Conversation. Generation admission, preview and retries never accept a Project identifier: Chat resolves membership from the Conversation and checks requested sources against it.

## Independent context assembly

Project content must never enter `input_content`, the stored user Message body, or historical `batch_context_items`. ADR-0025's augmented turn input retains its existing replay semantics. Project Sources reuse the attachment format, not the augmented-user-input storage path.

Chat constructs each request in this order:

1. The attempt's base System Prompt plus the Batch's saved Project Instructions, with an explicit boundary.
2. Ordered historical user/assistant pairs from the existing Context Snapshot, respecting Selected Answers and context skips.
3. One final user message, assembled at execution/preview time from the server-rendered project reference prefix followed by the current question and ordinary turn attachments from the existing `input_content` handling. The prefix includes saved Project Background and fixed Project Sources when present, explicit reference-data boundaries, and an explicit boundary before the current question. With no reference input, use the current turn content directly.

The final step concatenates saved execution fragments; it does not update stored `input_content` or Message text. Project references do not introduce an additional user-role message or a synthetic assistant acknowledgement. This preserves ordinary user/assistant alternation for compatible model templates. Use deterministic, escaped reference serialization and a rendering version rather than interpolating unescaped source text into structural markers. Background and source text remain labeled reference data even when authored by the user; they are never promoted to system guidance. Historical project blocks are not replayed with historical turns. Every Target and retry uses the Batch's project block once, regardless of subsequent edits, moves, source replacement or Project deletion. Other attempt settings retain their existing retry semantics.

The system message therefore mixes two lifetimes on retry. The base System Prompt and generation parameters follow the existing retry behavior and come from current settings when the retry attempt is created. The Project Instructions fragment always comes from the Batch's saved Project Context Snapshot. A retry after editing both therefore pairs the new base prompt with the original Project Instructions. This is intentional: Project input belongs to the Batch's shared input, like its Context Snapshot and attachments, while base configuration belongs to each attempt. Implementations must not unify the two by freezing the base prompt or by reading live Project Instructions. The inspector labels the two fragments with their respective sources for a saved attempt.

Placing reference input after history preserves straightforward turn-specific assembly and existing historical replay. The large fixed-source block moves behind a growing history prefix, so its full content cannot be relied on as a stable common prefix across turns for upstream caching. Earlier common request prefixes may still benefit from Provider caching. This is an intentional first-version cost/performance tradeoff, not a promise of cache hits; context reordering or Provider-specific cache controls require a separate measured change.

Replacing background or removing a fixed source stops direct injection into new Batches. Historical Messages and Selected Answers may still quote or paraphrase old project content. Moving a Conversation retains that visible history. The interface explains these boundaries rather than promising semantic erasure.

## Preview, admission and browser inference

Draft preview includes Project and membership revisions. Admission atomically checks those revisions and saves the complete project payload, blob references and Batch after the existing idempotency check. Reject stale previews with HTTP 409 and error code `project_context_changed` when intervening edits, source changes or moves changed the input; include the current Project identity/revisions for refresh. The frontend refreshes the project summary/context preview and preserves the draft question, local files, prepared-source state and model selection. An expired prepared-source token is marked for re-preparation without discarding the rest of the draft. Do not create a partial Batch, silently resubmit, or clear the draft on this conflict. Repeated accepted client requests return their original Batch and snapshot before revision checks.

Extend ADR-0021 with `GET /api/generation-batches/{id}/context?format=project-v1`, returning ordered `history` and saved `project_context`. The project object contains the exact instruction fragment, rendered reference prefix with the current-question boundary, historical Project revision and saved source metadata. The existing request without `format` retains its array response. The current user input and attempt's base System Prompt stay in their existing records. Type and validate the additive contract in `packages/api-contract`.

NearAI consumes these server-rendered fragments in the same order as ordinary inference, concatenating the reference prefix and saved current-turn input into a single final user message. It never renders sources again or assembles project content from the sidebar, editor or current library. Distinguish legitimate absence on old/ungrouped Batches from a missing required snapshot; missing required input fails visibly. Both contract forms remain session-protected and `Cache-Control: no-store`. Invalidate affected project/context queries after mutations. Preview and both inference paths must agree on the exact text, role sequence and ordering.

## Fixed sources, citations and limits

Fixed Project Sources are included in the first version. Reuse supported file parsing and explicit webpage retrieval through Chat, including bounded previews and existing `documents.Snapshot` identity, parser version, sections, original bytes and provenance. Saving or replacing a fixed source is an explicit user action. There is no filesystem watcher, automatic URL refresh or background indexing. Every new project Batch includes the current fixed set, shown before submission.

At project-source save/replacement time, validate a maximum of three fixed sources and 60,000 extracted characters across that fixed set. Retain existing per-source 4 MiB and 60,000-character bounds. These smaller project quotas reserve at least one source slot and 60,000 extracted characters for a new turn attachment under the combined four-source/120,000-character limits. Reject an over-quota project edit immediately and leave the prior fixed set intact. Show fixed and remaining capacity in both the project editor and composer, and recheck the combined limits at submission. The separate total-context bound can still constrain a long conversation; source capacity is not a guarantee of remaining overall context space.

Count the actual assembled request, including serialized reference wrappers and instruction boundaries, against the existing 240,000 Unicode-character limit. The inspector shows non-overlapping counts for instructions, background, project sources, history, and current question/turn attachments, with a total. Distinguish base/project instructions within the instruction category. Token estimates are labeled approximate. Draft preview, admission, retry and web-tool expansion share assembly/counting logic.

An over-limit error retains the draft and offers the context breakdown with an explicit `Continue in a new conversation` recovery action. That action creates a Conversation in the same Project, carries the unsent question/local files and still-valid prepared-source state, and previews it with current project input but no inherited history. It does not send automatically. Preserve the original draft until creation and transfer succeed. If project input plus the draft alone still exceeds the limit, point to editing the project background/sources or reducing the draft. Do not offer to alter frozen historical dispositions; a future selective-history feature needs its own decision.

Extend citations, References, previews and original downloads to saved project sources as well as existing turn/research sources. Resolve `cove:<identity>:<section>` against source copies belonging to that saved request or answer, never the current Project. Historical citations keep working after live project sources are removed.

## Existing workflows and deletion

- Membership: support assigning existing Conversations, moving between Projects and returning to ungrouped history. Moves affect new Batches only; historical Project identities remain. Settle affected active work first, using cancel-and-wait where requested. Pause and settle running Debates before moves. Moving never promotes history into project background.
- Branches: inherit the source Conversation's current Project. Copy historical rendered payloads/source sections and add independent blob references with the copied prefix, extending ADR-0035. The edited new question captures current project input. Deleting the source cannot mutate branch snapshots or collect blobs the branch still references.
- Side Conversations: the answer-tools frontend supplies `source_conversation_id` when creating the separate Conversation through `POST /api/conversations`. Chat loads that source and resolves its current membership in the creation transaction; it does not accept a client assertion of the inherited `project_id`. Reject a missing source or conflicting membership input explicitly and create no partial Conversation. Preserve the selected-passage-plus-question input and independent history, then capture current project input normally. Do not import the entire source chat. Revisions/moves racing the first submission use the normal `project_context_changed` handling.
- Debate: first-version membership organizes and filters history only. Its saved rules/turn contexts stay unchanged. Project input injection requires a separate session/round snapshot decision and is outside this delivery.
- History search/filtering: add Project and ungrouped scopes to existing list/search APIs and query keys. Persistence applies scope before result caps. This does not introduce project-source full-text search.
- Exports: include actual saved project instructions, background, source text/provenance and historical Project revision in JSON and a labeled Markdown section. Preserve existing exclusion of original source bytes and credentials. Project backup/import is separate.
- Project content removal: changes affect future Batches; saved snapshot copies remain until their owning history is deleted. Show that scope. First-version controls do not offer partial historical snapshot erasure.
- Clear chat history: preserve Projects, current instructions/background, fixed project-source entries, Provider/search settings and Keys. Remove Conversations, snapshots and Batch-owned blob references after ADR-0006 cancel-and-wait. Collect only unreferenced blobs, preserving originals still referenced by fixed project sources. Confirmation enumerates retained project data.
- Dissolve Project and keep conversations: require the same idle admission as a membership move; reject active work without stopping it. Then atomically move current members to ungrouped history, advance membership revisions, and remove the live Project/configuration and project-source references. Retain historical Batch payloads and blob references, so inspection, downloads, exports and retries still work. New Batches use no live project input. Preview retained historical copies and collect only unreferenced blobs.
- Delete Project and its conversations: remove the current Project, current member Conversations and their project-source/Batch blob references after cancel-and-wait. Confirmation lists member counts and retained historical copies in moved/branched Conversations outside the Project. Those snapshots and their blob references remain independently owned and inspectable; their Conversations can be deleted separately. Collect only unreferenced blobs. Do not label this a complete purge of all past project-derived content.

Keep deletion based on explicit record ownership and blob references instead of introducing a version-dependency purge engine. Surviving Conversation snapshots remain inspectable, exportable and usable for exact retries after live Project deletion. Cove has no full-local-reset product action today; designing one is outside this delivery. Existing clear-history behavior must not be described as a full reset. External exports, backups and Provider-held content remain outside local deletion guarantees.

## Privacy and compatibility

Show the active Project and input summary beside the composer. Users can inspect exact instructions, background and fixed sources and see selected Provider destinations before sending. Explain that project input goes to every selected model on every Batch, consumes context and can increase usage. Each model retains its existing transport; NearAI verification does not verify the truth of reference data. Project content remains unencrypted local SQLite data. Update the user guide, inspector and privacy notice when shipping.

The schema-22-to-23 migration and additive schema-23-to-24 index migration are transactional. Existing Conversations default to no Project and old Batches to no Project Context Snapshot. Older services reject the upgraded database; document the compatible-backup requirement at release. This ADR extends ADR-0015, ADR-0021, ADR-0025, ADR-0035 and ADR-0044. Project Instructions retain Batch scope when the base System Prompt changes on retry.

## Acceptance and deferred work

First-version checks cover project edits/moves and `project_context_changed` races with draft retention; save-time fixed-source quotas and remaining attachment capacity; reuse across independent Conversations without repeated raw-byte storage; one final user message with identical role sequence/text across preview, ordinary inference, retries and NearAI; project blocks appearing once without history accumulation; replacement/removal affecting new direct input only; citations/downloads after edits/deletion; character-limit accounting and draft-preserving continuation in a new same-Project Conversation; branch blob-reference ownership; server-resolved side-conversation membership; validated `project_id` on explicit creation/move commands and its rejection on generation commands; retries after editing both the base System Prompt and Project Instructions; scoped history and exports; and reference-safe collection after clear-history, project dissolution and project deletion. Verify that a shared blob survives until the last owning reference is deleted, including branch and concurrent admission cases. Cancellation or migration failures leave data intact. Use synthetic fixtures, temporary `COVE_DATA_DIR` directories, and both context response formats.

Memory entries, answer-derived notes, extraction/conflict handling, retrieval indexes, selective historical payload erasure and Debate project-context injection need separate evidence and decisions. Long backgrounds or repeated requests to enable/disable individual facts can justify revisiting memory entries. Do not prebuild those tables or workflows.

## Review corrections

Conversation responses carry one `project_contexts` dictionary keyed by the SHA-256 of each saved payload and `project_context_id` references on Batches, including the active Batch. The API client hydrates shared immutable objects; citations, inspectors and exports retain the exact saved input. A conversation read decodes identical payloads once within that request; it does not retain a process-wide cache of deleted history. Single-Batch and context endpoints keep their existing payloads.

Generation and preview read only current project input, without historical-copy counts. Explicit project management reads use an indexed project-identity expression for historical counts. Schema 24 adds that index and indexes for source-blob ownership lookups; existing schema-23 data is preserved.

Dissolution is a membership operation and requires idle work, matching an individual move. Only destructive project deletion cancels affected work: enumerate both ordinary and browser generation registries by Conversation, cancel and wait, then delete. A failure to settle preserves records. Do not infer affected work solely from an active-Batch projection.

Legacy context preview still rejects oversized input. Only the explicit `project-v1` preview can inspect an over-limit draft. Background usage measures raw Unicode characters; JSON escaping, quotes and reference delimiters belong to reference framing so all categories sum to the assembled request. Saved legacy accounting fields do not override this calculation. Both project and ungrouped NearAI research count the frozen base prompt, history and current input before tool continuations. Project-aware NearAI reads go through the generation query cache with a separate immutable context key.

Project-conflict recovery restores the draft, attachment state and idle UI before refreshing server data. A failed refresh reports that the context still needs review without discarding local input. Both context-review entry points use the preview mutation hook, which reconciles the reviewed membership/project revisions in the conversation cache; reviewing fresh input must not leave admission on a stale revision.
